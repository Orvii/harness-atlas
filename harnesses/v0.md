## What it promises

v0 is an AI-powered development platform for building production-ready applications from natural-language prompts, and it is explicitly agentic rather than a code-completion surface: it combines web search, browser use, automatic error fixing, terminal commands and external tool integration, with every action running inside an isolated sandbox whose autonomy the user dials with permission modes. The docs also promise a full delivery path, not just generation - chats bind to a real Vercel Project with deployments, environment variables, domains and Git branching, working branches get preview deployments, and Publish creates or reuses a pull request, merges it, and starts the production deployment. Hosting is inseparable from the product: the preview you see is your app running in a real Node.js VM, and "the preview behaves the same way your project will once deployed to Vercel".

## Architecture

v0 is a browser-hosted builder whose execution environment IS the product. A chat runs inside a VM-backed sandbox powered by Vercel Sandbox - a lightweight VM running a full Node.js environment that hosts your project files, serves the live preview, and executes commands on your behalf (https://v0.app/docs/sandbox). The sandbox surfaces in three places inside the chat: a Preview tab served by the in-sandbox dev server, a Console panel with Logs and Terminal tabs, and a read-only Code viewer with line comments that become prompt annotations (https://v0.app/docs/code-editing). The agent loop is documented as a fixed capability set - web search, browser use (it opens and drives the apps it builds and sends screenshots), automatic error fixing (missing files/dependencies, syntax, runtime bugs, import/export problems), terminal commands via a Bash tool, and external tool integration - with a "Fix with v0" button in the deployment popover that pipes error logs back into the chat (https://v0.app/docs/agentic-features). Every command runs in a fresh shell starting from the project root, so v0 chains operations explicitly rather than relying on shell state, and the pre-installed Claude Code agent can be launched from that same terminal (https://v0.app/docs/terminal-commands, https://v0.app/docs/pre-installed-agents). Delivery is wired to Vercel Projects: chats bind to a project with deployments, environment variables and domains, working branches get unique preview URLs, and Publish creates or reuses a pull request, merges it and starts the production deployment (https://v0.app/docs/deployments, https://v0.app/docs/github, https://v0.app/docs/projects); the FAQ adds that "v0 never pushes directly to `main`" (https://v0.app/docs/faqs). Outside the app, the same machine is exposed as a platform API with v1 and v2 generations - v2 adds explicit endpoints for sync, async and streaming responses and a migrating-from-v1-to-v2 guide - and as an MCP server for other clients (https://v0.app/docs/api/v2, https://v0.app/docs/api/v2/guides/mcp-server).

## Context management

Context is assembled from three sources: saved Instructions, saved skills, and the live sandbox workspace. Instructions are reusable prompts saved to the account, applied per conversation by checking them in the prompt bar, with multiple instructions enableable at once until unchecked, and two built-in presets (Be Concise, Plan Mode) (https://v0.app/docs/instructions). Skills are the heavier mechanism - a design system is imported once from a repo, a consumer app, Figma frames and docs, then saved as a skill in the current scope with SKILL.md plus a v0.json source of truth, and pulled in when relevant (https://v0.app/docs/design-systems-2). Within a chat, code context is added surgically rather than by dumping files: the code viewer lets you drag across line numbers and attach comments, and the prompt captures the file path, selected lines and captured code so the reference survives later file changes (https://v0.app/docs/code-editing). Deliberate bounds exist: sandbox filesystem state is isolated per chat ("State from one chat never leaks into another"), each terminal command starts from the project root in a fresh shell, and file locks let you protect specific files - package.json, tsconfig.json, working components - from AI modification during generation, so you can direct the agent's scope rather than hope it stays in bounds (https://v0.app/docs/sandbox, https://v0.app/docs/terminal-commands, https://v0.app/docs/api/v1/guides/lock-files-from-ai-changes).

## Ecosystem

The integration story is Vercel-shaped. Model access runs through Vercel AI Gateway by default, which is also how the pre-installed third-party coding agents' traffic is routed, so a team's model restrictions and subprocessor boundaries apply uniformly and usage is metered against the same AI Gateway credits (https://v0.app/docs/pre-installed-agents, https://v0.app/docs/ai-models). Tool access comes from two places: Vercel Marketplace Integrations, which inject third-party tool calls into chats with no extra setup, and user-registered MCP servers with four documented auth modes and presets spanning Contentful, Context7, Datadog, Glean, Granola, Hex, Linear, Mobbin and others (https://v0.app/docs/MCP). Adjacent first-party surfaces include GitHub import and PR automation, Figma, Snowflake, Shopify, Vercel Connect, custom domains and Slack - where `@v0` continues the same chat and branch from a thread (https://v0.app/docs/github, https://v0.app/docs/figma, https://v0.app/docs/snowflake, https://v0.app/docs/shopify, https://v0.app/docs/vercel-connect, https://v0.app/docs/slack). v0 is also embeddable: the platform API ships SDK packages including v0-sdk, @v0-sdk/react with a V0Transport for useChat, @v0-sdk/ai-tools, and create-v0-sdk-app, with example apps like v0-clone and react-components (https://v0.app/docs/api/v1/packages/v0-sdk, https://v0.app/docs/api/v1/examples/v0-clone).

## Governance

Governance is team- and Enterprise-oriented. Teams get workspaces with roles, and team owners control the default chat visibility for new chats (Private, Team can view, Team can edit) from Settings - Workspace - Default Chat Visibility, with per-chat overrides still available from the Invite dialog (https://v0.app/docs/teams). Model access is owner-gated: custom models stay locked on Enterprise teams until an owner enables Allow custom models, and individual model restrictions and isolated tenant restrictions continue to apply (https://v0.app/docs/model-picker, https://v0.app/docs/enterprise). Agent autonomy is governed by the same permission layer that the docs describe for the terminal - Ask/Auto/Full modes plus an editable allow/ask/deny rule list under Settings - Agent Permissions, and the setting persists across new chats (https://v0.app/docs/terminal-commands). Spending is governed through the Usage & Activity dashboard, where team-wide credit consumption is visible only to the Owner or Billing role while ordinary members see only their own activity (https://v0.app/docs/usage-dashboard). A notable default-deny: pre-installed agents are "disabled by default for Enterprise accounts" and require an explicit admin opt-in, with the docs framing this as letting organizations evaluate the feature against their own policy (https://v0.app/docs/pre-installed-agents).

## Limitations

Several axes simply do not apply to a browser-hosted builder, and the docs make that legible. There is no local runtime to sandbox because the sandbox IS the product - isolation is per-chat VM state rather than a local permission mode, and its flip side is that nothing persists across chats by design. IDE integration is MCP-mediated, not a native extension: VS Code requires MCP extensions and the whole path needs Node.js and npx mcp-remote (https://v0.app/docs/api/v2/guides/mcp-server). Subagents exist as a named capability but with no configuration surface anywhere in the docs, so they cannot be authored or targeted. MCP is capped by the docs' own statement that "Streaming operations are not exposed as MCP tools" (https://v0.app/docs/api/v2/guides/mcp-server). Model choice is real but gated - the updated picker is Enterprise-only and custom models need owner acceptance (https://v0.app/docs/model-picker). Usage reporting degrades on unsupported plans or billing models, where the page falls back to a legacy view or a message saying usage data is not available (https://v0.app/docs/usage-dashboard). And there is no published product version identifier at all: the changelog is dated entries only, so "what version of v0" is unanswerable from the docs (https://v0.app/changelog).

## Notable

The sandbox ships pre-installed third-party coding agents - the docs tell you to type `claude` in the v0 terminal to launch Claude Code inside the same project VM, with that agent's traffic routed through Vercel AI Gateway; the feature is disabled by default on Enterprise and an admin must opt in. v0 is bidirectional in MCP: it consumes bring-your-own MCP servers as a client AND publishes a v0 MCP server that plugs v0 into Cursor, Claude Desktop and VS Code. Plan mode is not just a prompt preset - the agent emits a structured `exit_plan_mode` agent-action resolved with a `plan-exit-response` task, so plan-then-approve is an API contract. And despite being a hosted builder with no local runtime, v0 exposes hard command-sandboxing primitives: three terminal permission modes plus an editable allow/ask/deny rule list persisted across chats.
